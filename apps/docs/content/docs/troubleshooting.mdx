## Installation Is Required

If a command reports that installation is incomplete, run:

```sh
mate install
```

Mate records install state separately for each companion context. A changed
companion configuration, changed dependency plan, missing tool, or Mate update
can make that state stale. In a non-interactive process, use:

```sh
mate install --yes
```

## Inspect The Active Context

```sh
mate doctor
```

Check the reported state, companion path, repository ID, allowed agents,
capabilities, and missing commands. The expected launch state is
`linked-working-repository`.

## No Companion Is Found

Run the link wizard from the working repository:

```sh
cd /path/to/working-repo
mate companion link
```

The command requires a TTY. If you are inside a subdirectory, Mate searches
upward for the nearest `.mate/config/registry.yaml`.

## Multiple Companions Match

The working repository can have more than one valid companion pointer. Run the
command in a TTY so Mate can prompt for a choice. For scripts, pin the context:

```sh
MATE_ARTIFACT_PATH=/path/to/companion \
MATE_REPO_ID=my-repo \
mate claude
```

If a pointer refers to a directory that no longer exists, Mate drops that stale
pointer from the repo-local registry.

## A TTY Is Required

These workflows are interactive:

- `mate companion setup` selection
- `mate companion link`
- `mate companion tui`

Run them from a local terminal. Setup can accept explicit selection flags, but
initializing an unrecognized directory may still ask for confirmation.

## Agent Launch Fails

Launch only from the linked working repository:

```sh
mate claude
mate opencode
```

If the companion's allowed agents list disallows the requested agent, re-run
setup and allow that provider. If the agent command itself is missing, use `mate doctor` to
find the missing requirement.

Forward agent-specific flags after `--`:

```sh
mate opencode -- --continue
```

## Companion Git Synchronization Fails

When Git auto mode is enabled, Mate fetches the configured upstream and merges
it before syncing managed companion files. Resolve unfinished operations or
conflicts in the companion repository, then retry the launch.
`mate companion sync` runs the same synchronization without launching an agent.

To bypass synchronization for one launch:

```sh
mate claude -- --no-git
mate opencode -- --no-git
```

The switch must appear after the argument separator. Mate protects managed
paths during conflict recovery, but unrelated conflicts still require manual
resolution.

## A Plain Session Starts Without Companion Guidance

Plain `opencode` and plain `claude` in a wrapped repository load Mate through
`~/.mate/runtime/`. Installing or upgrading the package does not create it; any
`mate` run does. Run `mate doctor` (or `mate opencode` / `mate claude`) once after
installing or upgrading. If Mate is uninstalled, run `mate unwrap` in the
repository.

Mate can also refuse the repository's projection. It trusts a projection only
when your Mate configuration lists its companion and that companion links the
checkout the projection is in. A refused projection gives a plain session no
guidance and no guardrail, the same as an unwrapped repository. The session shows
one notice instead: Claude Code as its start message, OpenCode as a toast.

```text
mate: this folder's projection names a companion that is not registered in your Mate configuration (companion-not-registered); plain sessions here run without Mate. Run `mate doctor`.
```

`mate doctor` names the reason and the companion. The reasons are the
[session context codes](/docs/reference/commands#session-context)
`companion-missing`, `companion-not-registered` and `repository-not-linked`. To
fix it, run `mate companion link` in the repository to register and link a
companion, or run `mate wrap` from a checkout the companion links.

## Mate Is Missing In A Git Worktree

Mate adopts a new worktree of a linked clone the first time it runs there (see
[Worktrees](/docs/concepts/repositories#worktrees)). Run `mate doctor` in the
worktree: its Checkout section names the clone's Registered Checkout, the
checkout whose Claude wrap serves this one, and any warning.

### The main worktree is not wrapped for Claude

In a linked worktree, plain `claude` runs the hooks of the main worktree's
`.claude/settings.local.json`. After `mate unwrap` or `mate working cleanup` in
the main worktree, plain `claude` in every linked worktree starts without Mate's
session-prepare hook, and `mate doctor` in each warns and names that file. Run
`mate wrap` in the worktree: it wraps the main worktree for Claude again, then
the worktree.

### Claude Code is older than 2.1.211

Claude Code reads the main worktree's settings in a linked worktree from 2.1.211
on, and its skills from 2.1.277 on. With an older Claude Code, a plain session
in a new worktree reads only the worktree's own settings, which Mate writes once
it has run there: start the first session with `mate claude`, or run `mate wrap`
first. Update Claude Code to get Mate in the first plain session too.

### Windows and bare clones

On Windows, and in a worktree of a bare clone, each worktree uses only its own
Claude wrap. The first plain `claude` session in a new worktree therefore starts
without Mate; start it with `mate claude`, or run `mate wrap` there first.

In a worktree of a bare clone, Claude Code reads MCP servers from the bare
folder's entry in `~/.claude.json`, which no wrap writes. Mate's MCP servers are
therefore missing there, in plain and in `mate claude` sessions. This is a known
limit.

### The main worktree belongs to another user

`mate wrap` and `mate claude` in a linked worktree write the main worktree's
`.claude/settings.local.json`. When that file or folder belongs to another user,
they stop with the write error. Ask the main worktree's owner to run
`mate wrap` there, or work in a clone of your own.

### The worktree was moved by hand

Git finds a worktree through a record in the clone's shared Git folder. A
worktree moved without `git worktree move` keeps a record naming its old
folder, so Git, and Mate, no longer count it as a checkout of the clone: Mate
neither adopts it nor lends it the main worktree's projection, and `mate doctor`
shows it as not recognized. Run `git worktree repair` in the moved worktree, or
`git worktree repair <path>` in the main worktree.

## A Capability's Claude Plugin Does Not Load In Plain `claude`

Run `mate doctor`. Its Claude Plugins table has a Plain Sessions column showing
how each plugin folder reaches plain sessions:

- A marketplace name means the wrap enables the folder. Check that Claude Code
  trusts the repository folder, since Claude Code ignores the repository's
  marketplaces until it does. A Capability enabled since the last preparation
  loads from the next session, or right away after `mate wrap`.
- `no` and a reason means the folder is not published, so it loads only with
  `mate claude`. When the reason is that the name is already in use, your Claude
  Code configuration declares a marketplace of that name with another source. A
  common case is context-mode added from GitHub. Remove that marketplace, or keep
  using `mate claude` for this plugin.
- A `mate-plugin-…` marketplace name means Mate publishes the folder through its
  own marketplace file, which it writes at the next pass. If `mate wrap` notes
  that Mate could not write that file, make the folder's `.claude-plugin`
  directory writable and run `mate wrap` again. Until then the folder loads only
  with `mate claude`, and plain sessions report nothing about it.

## Warning: Restart With `mate opencode` Or `mate claude`

A plain `opencode` or `claude` session in a wrapped repository syncs the companion
in the background, fast-forward only, and cannot prompt. A diverged history, a
local edit the update would overwrite, or an unreachable remote leaves the session
on the current companion with this warning. Restart with the managed launch the
warning names (`mate opencode` or `mate claude`); its attended sync can resolve it.

## Artifact Write Blocked By The Guardrail

Agent artifacts (plans, specs, notes, and most Markdown) belong in the companion,
not the working repository. The guardrail refuses a write that would create one
in the working repository, and the refusal names the target and the companion:

```text
mate guardrail: artifact writes must go to the companion framework path.
 target:    notes/handoff.md
 resolved:  /work/acme/notes/handoff.md
 companion: /home/me/.mate/companions/acme
 suggested: /home/me/.mate/companions/acme/notes/handoff.md
Relative paths resolve against the working repository; a preceding `cd` is not followed.
Rewrite to the suggested absolute path and retry.
```

The guardrail resolves a relative path against the working repository, even after
a `cd` into the companion in the same shell command. `resolved:` shows the path it
judged, and appears only for a relative target. Links are followed before `..`,
as the system does, so `back/../notes.md` is judged where it lands when `back`
is a link. On a filesystem that ignores letter case (the macOS default), a path
spelled in another case is the same folder: `ACME-COMPANION/notes.md` is in the
companion `acme-companion`. `suggested:` is the matching
companion path, offered only when the target lies inside the working repository.
`companion:` is the configured companion path normalised, or, when a link before
a `..` in it leads elsewhere, the folder the system reaches; the companion's
`framework.yaml` and its Git state are read there too. This holds for the
companion path the guard gets from the launch environment or a projection. A
companion path stored in Mate's registries is still normalised before Mate
follows it, and a launch whose companion path leads to a missing folder uses the
normalised one instead, so avoid a companion path written with `..` through a
link.
Write artifacts with absolute companion paths.

A session without a Working Repository, such as `mate claude -- --companion`,
gets the same check: an artifact written outside the companion is refused, in
Claude Code and OpenCode alike. A relative path then resolves against the
session's folder, which for a companion-scoped launch is the companion, and the
refusal says so. Of the exemptions below, those that need a Working Repository
(a file its Git ignores or tracks, its product documentation) do not apply in
such a session; the others do.

Claude Code and OpenCode give the same verdict for the same call. Counted as an
artifact: `CLAUDE.md`, `CONTEXT.md`, `design.md`, `explore-brief.md`,
`proposal.md`, `spec.md`, `tasks.md`, anything under an `openspec/`, `changes/`,
`specs/`, `docs/adr/`, `docs/adrs/`, `docs/decisions/` or `docs/prd/` folder,
and any other Markdown file except `README.md`. Letter case does not matter:
`NOTES.MD` and `Spec.MD` count, `README.MD` does not. The guardrail refuses an
artifact that a call would create in the working repository:

- a whole-file write (Claude `Write`, OpenCode `write`), even over an existing file;
- an edit of a file that does not exist yet;
- a file a patch adds, and the destination of a patch's move. A move is judged
  at both ends: its source counts as an edit, so moving a secret file away, or
  a companion file out while the companion's history has forked, is refused;
- a shell redirect (`>`, `>>`, `>|`, `2>`, `&>`) that names a Markdown file,
  quoted or not (`> "notes dir/handoff.md"`), with quotes and backslashes read
  as Bash reads them;
- a Markdown file operand of `tee` (`tee -a README.md notes.md` judges both
  files). `tee` counts where it runs as a command: at the start of a command,
  after `|`, `;`, `&&`, `||`, `&` or `(`, in a `case` arm, behind `NAME=value`
  and array (`a=(1 2)`) assignments, or
  behind `sudo`, `env`, `command`, `exec`, `nohup`, `nice`, `time`, `stdbuf`
  or `xargs`, past the options of theirs that take a value (`sudo --user bob`,
  `nice -n 5`) and inside the command line of `env -S "…"`. An option the
  guardrail does not know is read as taking no value. As an argument
  (`grep tee notes.md`) `tee` writes nothing.

A command substitution or process substitution (`$(…)`, backticks, `<(…)`,
`>(…)`) is never read as a file name, but the command inside it is read the
same way, and the `tee` operands after it still count. The secret, commit
attribution and artifact checks read a command through one shared reader, so
they agree on where each command starts and what each word is. A `#` comment
hides the rest of its line from the artifact check, inside a substitution too.
The secret check reads comments like any other text and errs toward refusing,
so `git status # leave server.key alone` is refused there; see
[Secret Guardrails](/docs/concepts/secret-guardrails). An ANSI-C string `$'…'`
is read as Bash reads it (`\'` does not end it). A heredoc body is not read as
commands when its marker reads as one both on its own line and in the whole
command, with the delimiter taken as Bash takes it (`<<E"OF"` ends at `EOF`,
`<<EOF+` at `EOF+`). Otherwise the lines after the marker are read as commands
too: when the marker sits in a quote that spans lines, or in arithmetic
(`$((1<<2))`), or its delimiter holds `$` or a backtick. A substitution whose
heredocs the whole command could not place is read on its own the same way. A
command that nests substitutions more than 64 levels deep, counting those in a
comment or on a line of a quote that spans lines, is refused unread, before any
of the three checks:

```text
Mate guardrail: this shell command nests substitutions more than 64 levels deep, too deep to check, so it is blocked.
Split it into smaller commands.
```

Reading shell commands is best effort. The guardrail catches redirects, `tee`
and the common wrappers above, but it does not expand variables (`> "$OUT"`),
globs or `~`, does not follow a `cd`, judges only Markdown targets in shell
commands, and cannot see a write a command hides: through a variable, `eval`,
`python -c`, a script, or any program that writes files itself. It is a
guardrail that keeps an agent on the documented path, not a sandbox.

If the guardrail itself fails on a call, it refuses the call instead of letting
it run unchecked, in Claude Code and OpenCode alike:

```text
Mate guardrail could not check this call: <the error>
```

Retry the call; if it keeps failing, report the error. A companion write the
secret scan cannot run on is refused as well, with its own message.

It allows:

- anything in the companion, reached through its link in the working
  repository or its own path. A folder whose name merely starts with the
  companion's, such as `acme-old` beside `acme`, is not the companion;
- an edit of an existing file, including a patch's update or delete;
- a file Git ignores or already tracks;
- product documentation: a `docs` folder that holds a `package.json`, and
  `storybook` or `.storybook` folders;
- the agent's own configuration folder: `CLAUDE_CONFIG_DIR` or `~/.claude` for
  Claude Code; `~/.config/opencode` (or `$XDG_CONFIG_HOME/opencode`) and
  `OPENCODE_CONFIG_DIR` for OpenCode. A path written under that folder counts
  even when a link takes it elsewhere, so a `CLAUDE.md` or skill linked there
  from a dotfiles repository stays editable, unless the write lands in the
  working repository: a link from that folder into the working repository is
  judged where the write lands. On a filesystem that ignores letter case, the
  folder spelled in another case counts too. A configured folder is followed
  as written, so `link/..` in it means the folder the system reaches.

## Commit Refused For A Co-Authored-By Trailer

An agent commit whose message credits an AI model as co-author is refused before
the commit is created:

```text
Mate guardrail: Co-Authored-By trailers that credit an AI model are not allowed in this repository.
No commit was created. Rerun the same commit without the Co-Authored-By trailer; do not amend or rewrite history to remove it.
```

Nothing needs to be undone. Rerun the commit without the trailer. A human
co-author trailer is allowed. See
[Commit Attribution](/docs/concepts/commit-attribution).

## A Launch Waits For Another Sync

Every companion sync holds one lock per companion under `~/.mate/locks/`. A
launch waits for another running sync; session-start preparation skips instead.
A lock left by a process that no longer runs is cleared automatically.

## Update Fails

Self-update works only when Mate was installed globally through npm. Check the
current version without changing anything:

```sh
mate update --check
```

If self-update reports that the installation is not npm-managed, reinstall the
published package:

```sh
npm install -g @uniqbit/mate
mate install
```

## Capability Indexing Fails

Run the indexer explicitly to isolate the failing capability:

```sh
mate cap index --graphify
mate cap index --tokensave
```

Then run `mate doctor` and verify the relevant capability and command are
selected and installed. TokenSave uses a repo-local `.tokensave` store; Graphify
and TokenSave cannot be forced together in one command invocation.

## `@mate:` Rows Are Missing

The [Companion Mentions](/docs/capabilities#companion-mentions) plugin adds
`@mate:` rows to Claude's `@` menu. When they do not appear, check these causes:

- The session was started with plain `claude` in a repository that Mate has not
  wrapped, or Mate does not publish the plugin to plain sessions. Run `mate wrap`
  or start the session with `mate claude`, and check the Plain Sessions column of
  `mate doctor`. See
  [A Capability's Claude Plugin Does Not Load In Plain `claude`](/docs/troubleshooting#a-capabilitys-claude-plugin-does-not-load-in-plain-claude).
- Claude Code does not trust the repository folder. A plain session loads the
  plugin only after you accept Claude Code's trust dialog for that folder.
- Claude Code is older than 2.1.292. Older versions start normally and ignore
  the plugin. Check the version with `claude --version`.
- The plugin is not declared or not installed. `mate doctor` lists the Claude
  plugins that capabilities contribute and whether each one can load. If
  `companion-mentions` is not listed, install the plugin as its
  [package README](https://www.npmjs.com/package/@uniqbit/mate-plugin-companion-mentions)
  describes.
- The session runs inside the companion, for example after
  `mate claude -- --companion`. Claude's own rows already list the companion's
  files there, so the plugin adds none. A typed `@mate:` mention still attaches.
- A mention attaches a note saying that Mate refused the companion: it is not
  registered in your Mate configuration (`companion-not-registered`), or it does
  not link this repository (`repository-not-linked`). This happens when a cloned
  repository carries another machine's projection. `mate wrap` alone fixes
  neither. Run `mate companion link` in the repository and pick your companion:
  it registers the companion and links the repository. Then run `mate wrap`, or
  start a session with `mate claude`, so the repository's projection names that
  companion. A companion you already use but Mate does not list is registered
  with `mate companion register <path>`.
- A mention attaches a note asking for a matching Mate version. The plugin found
  no readable secret policy, which happens when Mate is older than the plugin. In
  a plain session it also happens when Mate's launcher at
  `~/.mate/runtime/bin/mate` is missing or has no `session context` command.
  Until that is fixed, the plugin shows no rows and attaches no files. Update
  Mate to the plugin's version, then start a new session.
- In a plain session, a mention attaches a note pointing to `mate doctor`:
  `mate session context` did not answer within 5 seconds, or named a companion
  and then exited with a failure status, so the plugin does not use the answer.
  Run `mate doctor` to check the installation. Updating Mate alone may not fix
  it.
