## Setup And Linking

| Command                                         | Context                 | Purpose                                                                    |
| ----------------------------------------------- | ----------------------- | -------------------------------------------------------------------------- |
| `mate companion setup`                          | Companion root          | Create or reconfigure a companion explicitly.                              |
| `mate companion link`                           | Working repository, TTY | Select or clone a companion, write the link, and install its requirements. |
| `mate companion list [--json]`                  | Linked context          | List linked repositories.                                                  |
| `mate companion open`                           | Linked context          | Add the working repository and companion to the preferred editor.          |
| `mate companion tui`                            | Linked context, TTY     | Open a shell in the resolved companion.                                    |
| `mate companion sync`                           | Linked context          | Sync the companion with its Git upstream, interactively at a terminal.     |
| `mate companion register [path]`                | Any                     | Register an already-configured companion without reconfiguring it.         |
| `mate companion prepare --from <bundle> [path]` | Any                     | Prepare machine-local dependencies from a fully installed prebuilt bundle. |

`mate companion link` does not accept flags. Its selection and any required
installation confirmation are interactive. The default workflow is:

```sh
mate install
mate companion link
mate opencode
```

## Installation And Health

| Command                                             | Purpose                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `mate install [--yes]`                              | Install and verify core requirements or refresh the active companion requirements. |
| `mate doctor`                                       | Show context, policy, selected capabilities, and tool status.                      |
| `mate config [--vscode]`                            | Open the global `~/.mate` configuration directory.                                 |
| `mate report [--days N] [--input FILE\|-] [--json]` | Generate a built-in or structured report.                                          |
| `mate studio [--writable]`                          | Serve Studio; the Vault is read-only unless explicitly writable.                   |

`mate install --yes` skips interactive confirmation and is required when the
process has no TTY. It can run before a companion is linked; in that context it
installs only Mate's core requirements.

### Reports

Without `--input`, `mate report` collects configured usage and savings data. To
create a report from a skill or script, pass a versioned JSON `ReportDocument`
with `--input FILE`, or use `--input -` to read JSON from stdin. The document
contains `version: 1`, `title`, `generatedAt`, `metadata`, `summary`, and typed
sections: `metadata`, `metrics`, `key-value`, `table`, `statuses`, or `text`.
Section IDs must be unique and dynamic values are limited to JSON scalar values.

Use `--json` with either path for normalized JSON output. Otherwise Mate writes
self-contained HTML to a temporary file and opens it in the default browser.
A report with a `mermaid` diagram loads the pinned Mermaid runtime from
jsDelivr; offline, each diagram shows as its source text.
The HTML includes a browser-native `Print / Save as PDF` control; selecting
`Save as PDF` in the print dialog creates the PDF. No PDF runtime or server is
required.

### Studio

`mate studio` serves one local page showing the Mate and workflow with
the selected companion's real state on it: a Dashboard over its changes and
specs, a Workflow view presenting the prompts a change is driven by — one card
per prompt, copied by clicking it — and a Vault view over the companion's
markdown files.
It runs from any directory, binds a port the operating system assigns on the
loopback interface, opens the platform browser, and serves in the foreground
until interrupted. Pass `--writable` to `mate studio` or
`mate studio serve --port <port>` to enable Vault saves; all other endpoints
remain read-only, and the default remains read-only. Add `--terminal` (with
`--writable`) for a browser terminal that starts Claude Code or OpenCode against
the companion; it, and every `mate studio serve`, is guarded by a per-start
access token.
See [mate studio](/mate-cli/reference/studio).

## Agent Launch

```sh
mate claude [-- agent-args...]
mate opencode [-- agent-args...]
```

Launch commands use a linked Working Repository by default. The companion's
allowed agents list must include the requested agent. To launch from the
Companion Repository without a Working Repository, use the reserved token after
the separator:

```sh
mate opencode -- --companion
```

Companion-scoped launches run the adapter from the Companion Repository, keep
companion Git and runtime synchronization, policy enforcement, and capability
preflight, but skip Working-Repository projection, automatic indexing, and
Working-Repository-only hooks. The agent environment carries no
`MATE_REPO_PATH` or `MATE_REPO_ID`.

Mate synchronizes managed companion files before launch. If the companion's
configuration uses Git auto mode, it also fetches and merges the configured
upstream first:

```sh
mate claude -- --no-git
mate opencode -- --no-git
```

The `--no-git` switch is Mate's option only when it appears after the `--`
separator. `--companion` selects the companion scope and `--yes` suppresses the
interactive confirmation; these are also Mate options only after the separator.
All other arguments after the separator are forwarded to the agent.

Confirmation is shown only when standard input is a TTY. Non-interactive
launches proceed without a prompt.

### OpenCode: Wrap, Prepare, Launch

`mate opencode` from a Working Repository syncs the companion with Git, wraps the
repository for OpenCode when that wrap is missing or out of date, re-projects the
companion copies and runs the capability preflight, then starts plain `opencode`.
`mate claude` runs the same preparation, with the Claude projection instead of the
wrap. At a terminal the companion Git sync is interactive, and a sync that still
fails stops the launch. When another companion sync is running, the launch says so
and waits for it. It sets no `OPENCODE_CONFIG_DIR`, so your global OpenCode
configuration (`~/.config/opencode`) applies as usual; an `OPENCODE_CONFIG_DIR` or
`OPENCODE_CONFIG_CONTENT` you set yourself is passed through. With `-- --no-git`
only the local preparation runs.

Because the wrap carries everything, plain `opencode` in a wrapped repository is
equivalent: before the session starts, the Mate plugin re-projects the companion
copies and runs the capability preflight, waiting at most 30 seconds, and enables
Mate's MCP servers once that is done. It never waits on the network: the companion
Git sync then runs in the background, fast-forward only, on every session start.
Changes it brings in are re-projected into the running session. It cannot prompt, so
a diverged history, a local edit the update would overwrite, or an unreachable
remote is reported as a warning to restart with `mate opencode`, whose attended sync
can resolve it, and the session keeps running on the current companion. This also
holds when OpenCode's shared background service was started from another directory.

## Wrapping

```sh
mate wrap [--companion PATH]
mate unwrap
```

`mate wrap` makes sessions you start yourself (`claude`, `opencode`) load the
companion. For OpenCode it writes `.opencode/opencode.json` regions (Mate plugin,
companion skills, `references.mate`, permissions, MCP servers, and settings from the
companion's own `.opencode/opencode.json` that your repository does not set) and
copies the companion's `.opencode/` files (commands, agents, skills, plugins, tools)
into your repository's `.opencode/` as regular, git-excluded files. Mate records
every copy it owns:

- a file your repository already has at the same path wins; Mate warns and leaves it;
- an owned copy you edited locally is replaced on the next re-projection, with a
  warning naming the companion file to edit instead;
- a file removed from the companion is withdrawn from your repository.

Paths into the Mate installation go through `~/.mate/runtime/`, which every `mate`
run keeps pointing at the installed version, so a wrapped repository survives a
reinstall or Node switch. Installing or upgrading does not create that directory;
the first `mate` run does. Until then, plain `opencode` in a wrapped repository starts
without the companion guidance and reports the missing directory, so run `mate` once
after upgrading. If you uninstalled Mate, run `mate unwrap` (or `mate` once after
reinstalling).

`mate claude` does not run in a repository wrapped for Claude; `mate opencode`
always runs. `mate unwrap` withdraws the documents and the owned copies and keeps
the repository link.

## Session Preparation

```sh
mate session prepare --repo <dir> [--json] [--sync]
```

Runs what a managed launch prepares, without starting an agent. Without `--sync` it
touches no remote: it syncs and self-heals companion files, re-projects the OpenCode
documents and copies, and runs the capability preflight. When another companion sync
holds the lock, it skips at once. With `--sync` it first fetches and fast-forwards
the companion, then runs that local preparation only when the companion moved. A
diverged history, an overlapping local edit or an unreachable remote is a warning
to restart with `mate opencode`, not a failure. Every companion sync (managed
launches, `mate companion sync`, session-start repairs and this command) is
serialized through one lock per companion under `~/.mate/locks/`. The command
refuses a repository that is not wrapped for OpenCode and names `mate wrap`.
`--json` prints each step's outcome and the warnings. The OpenCode plugin calls
this for you.

### Exit Status And Signals

A launch exits with a status reflecting how the agent process ended: zero when
the agent exited zero, non-zero when it did not. The JSON result is still
printed, but it no longer stands in for the status.

A launch also forwards `SIGINT` and `SIGTERM` to the agent process it spawned
and waits for that process to exit before exiting itself, so nothing is left
running behind it. An agent that ends on a forwarded signal is reported as the
signalled stop it was — `128 + signal`, the usual shell convention — so a
caller can tell a clean shutdown from a crash. At a terminal this is unchanged
in practice: Ctrl-C reaches the whole foreground process group, so the agent is
stopped once and the shell is returned.

This is the one part of the unattended work that changes what an existing
workstation launch does, and it has no opt-out. A caller that read success from
a zero exit will now see agent failures.

`mate companion register` and `mate companion prepare` cover starting a launch
where no one is at a terminal; see
[Unattended Deployments](/mate-cli/reference/unattended).

## Capabilities

| Command                                    | Purpose                                         |
| ------------------------------------------ | ----------------------------------------------- |
| `mate cap openspec <subcommand> [args...]` | Run OpenSpec through the active context.        |
| `mate cap graphify <subcommand> [args...]` | Run Graphify through the active context.        |
| `mate cap index`                           | Refresh enabled Graphify and TokenSave indexes. |
| `mate cap index --graphify`                | Refresh only Graphify.                          |
| `mate cap index --tokensave`               | Refresh only TokenSave.                         |

The two index flags cannot be combined. When both Graphify and TokenSave are
enabled, the default index flow refreshes TokenSave and then refreshes Graphify
against the resulting state.

## Artifacts And Updates

| Command                                        | Purpose                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| `mate artifact finish <change-name> [options]` | Finalize a change artifact workflow.                                 |
| `mate update`                                  | Upgrade an npm-managed Mate installation and reinstall requirements. |
| `mate update --check`                          | Check for an update without installing it.                           |

Artifact finish options are `--type openspec`, `--force`, `--no-push`, and
`--json`. Update also accepts `--yes` to skip its confirmation prompt.

## Exit And Recovery Behavior

Unknown commands print the current usage text and exit non-zero. Missing or
stale installation state is repaired automatically when every requirement is
already available. If a requirement is missing, the companion is ambiguous, or
the Mate engine requirement is unsatisfied, Mate prints the reason and points
to `mate install` instead.
Doctor, setup, link, update, help, and version remain available so the state
can be repaired.
