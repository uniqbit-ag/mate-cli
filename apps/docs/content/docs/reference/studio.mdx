---
title: mate studio
description: A local page over the Mate workflow and the markdown files of every registered companion.
---

`mate studio` serves one local page that shows the Mate and workflow
with real state on it: the skills and prompts a change is driven by, alongside
that companion's changes and specs.

```sh
mate studio [--writable] [--terminal] [--detach-timeout <minutes>]
```

Without `--writable`, the vault is read-only. `--terminal` adds the
[agent terminal](#agent-terminal) and requires `--writable`. An unrecognized
argument is reported and the command exits non-zero without starting a server.

## Invocation Context

Studio does not resolve a repository link and does not require a working
repository, so it runs from any directory. The content is the same wherever it
is started: every companion registered on this machine.

It prints the URL it bound and opens that URL in the platform's default
browser:

```text
http://localhost:53219
Press Ctrl+C to stop.
```

If a browser cannot be opened, Studio says so on stderr, keeps serving, and
keeps reporting the URL so it can be opened by hand. If no port can be bound,
Studio reports the failure on stderr and exits non-zero without opening a
browser.

## Headless Serving

`mate studio serve` runs the same server without opening a browser.
It requires an explicit port and prints the bound URL when the server is ready:

```sh
mate studio serve --port <port> [--host <host>] [--writable] [--terminal]
  [--detach-timeout <minutes>] [--token <value>] [--allowed-host <host>]
  [--public-origin <origin>] [--companion <path>] [--no-git]
```

`--port` must be an available port from 1 through 65535. A bind failure is
terminal; Studio never silently chooses another port. `--host` defaults to
`127.0.0.1`. Name a non-loopback host explicitly when another machine must
reach Studio, for example:

```sh
mate studio serve --port 4180 --host 0.0.0.0
```

The server stays in the foreground until it receives `SIGINT` or `SIGTERM`,
then stops cleanly. The serve path does not print the interactive
`Press Ctrl+C to stop.` hint or attempt a browser launch.

A non-loopback deployment exposes companion paths, change names, and inventory.
The [access token](#access-modes-and-the-token) keeps a stranger out, but Studio
has no user accounts. Front it with a service that terminates TLS: plain HTTP
exposes the token in transit, and browsers withhold interfaces such as clipboard
access outside a secure context.

## Access Modes and the Token

Studio is _guarded_ under `mate studio serve`, and whenever `--terminal` is set.
A guarded Studio generates a fresh access token each time it starts and prints
an address that carries it; the interactive command opens the browser there:

```text
http://localhost:4180/?token=S6GdXknuAqJKsryTjSxQA4dFMjBg58enIGLb5rW1TvA
```

Opening that address exchanges the token for a cookie (`HttpOnly`,
`SameSite=Strict`, root path, host-only, `Secure` for an HTTPS public origin)
and redirects to the same address without the token. A wrong token is refused
and changes no cookie. A wildcard bind such as `0.0.0.0` prints a loopback
address, not the wildcard.

| Invocation               | Reads and live updates | Save                  | Terminal and sessions |
| ------------------------ | ---------------------- | --------------------- | --------------------- |
| `mate studio`            | open                   | Host + Origin         | —                     |
| `mate studio --terminal` | open                   | token + Host + Origin | token + Host + Origin |
| `mate studio serve`      | token + Host           | token + Host + Origin | token + Host + Origin |

Under `serve`, a browser without the cookie gets a page that holds no companion
data and explains how to open the tokened address; any other request is refused.
Plain `mate studio` issues no token and behaves as before.

**Pinning the token.** `--token <value>` or `MATE_STUDIO_TOKEN` pins the token
under `serve`, so it survives restarts and stays out of the log: Studio prints
the address without it. A value shorter than 32 characters is refused at start.
Open `http://<host>:<port>/?token=<value>` once per browser.

**Host checks.** Every request, under every invocation, must name a Host Studio
answers to, port included: the bound address, `localhost`, `127.0.0.1`, `[::1]`,
or a host configured with `--allowed-host` (repeatable, comma-separated) or
`MATE_STUDIO_ALLOWED_HOSTS`. Matching is exact — no wildcards or suffixes — so a
rebinding hostname can neither read nor write. When a published port differs
from the bound one (for example `8080:4180`), add `localhost:8080`.

**Origin checks.** A save, a terminal connection, and ending a session also need
a browser `Origin` matching the page's own. A missing, `null`, foreign, or
same-site sibling origin is refused, with or without a valid token.

**Behind a TLS-terminating proxy.** Set `--public-origin` or
`MATE_STUDIO_PUBLIC_ORIGIN` to the exact `https://host[:port]` users open. Its
host is accepted automatically. Requests on that Host use the public origin for
Origin matching and get a `Secure` cookie; a request on any other Host does not.
Studio never reads `Forwarded` or `X-Forwarded-*`. The proxy must enforce TLS
and keep the backend port unreachable except through it.

**Breaking change.** `mate studio serve` used to serve reads without any
check. It now requires the token for every request: open the printed address
once, or pin a token.

## Agent Terminal

`--terminal` adds a browser terminal that starts `mate claude` or
`mate opencode` against a companion, and nothing else — no shell, no path, no
extra arguments or environment from the page. It needs `--writable`, macOS or
Linux, and Bun 1.3.5 or later (which provides a native pseudo-terminal); on
anything else Studio refuses to start with `--terminal` and names what is
missing.

- **Where it sits.** The terminal is a sidebar docked on the right edge of the
  window, as tall as the window, and stays in view while the main view scrolls.
  Collapse it to a narrow strip, which keeps a connection-status dot, and
  expand it again; drag its left edge to change the width, between 360 pixels
  and 70% of the window. Neither ends, detaches, or restarts the session, and
  the terminal refits to its visible area. The browser remembers the width and
  the collapsed state (a blocked browser store falls back to the defaults);
  nothing is written to a companion or to Mate state. Below 1200 pixels wide,
  the sidebar becomes a drawer that the **Terminal** button opens over the
  page from the right, and the close control or `Escape` dismisses; a new page
  always starts with the drawer closed. Without `--terminal` the layout is
  unchanged.
- **What it launches.** The control offers only agents the companion allows and
  that are installed, and names the companion a new session targets. The
  launch is companion-scoped (`-- --companion --yes`), runs in the companion's
  directory with `MATE_ARTIFACT_PATH` set to it, and applies the same preflight
  as a local launch; a refusal is shown in the terminal. The companion is the
  one selected in the page, re-read from the registered inventory at launch.
  `serve --companion <path>` pins every launch to that registered companion
  instead, whatever the page shows. `serve --no-git` passes `--no-git` to each
  launch.
- **One viewer.** A session has one attached tab. Reloading the tab reattaches
  it; any other tab holding the cookie can attach, taking it over, and the
  previous tab is told so and does not reconnect by itself. After a lost
  connection a tab retries 8 times, starting at 2 seconds and doubling, then
  offers **Reconnect**.
- **Detach.** Closing the tab, losing the network, or missing heartbeats for 30
  seconds detaches the session; the agent keeps running. A detached session ends
  after the detach window: `--detach-timeout <minutes>`, 30 minutes under
  `serve` and 2 minutes interactively. Output produced meanwhile — the newest
  1 MiB — is replayed on attach, and the agent is nudged to redraw.
- **Sessions.** The sidebar lists live sessions with agent, companion, state, and
  age, and can attach to or end any of them.
- **Bounds.** At most four sessions per server, detached ones included; a new
  start at the cap ends the longest-detached one, or is refused if all are
  attached. One attached session per connection. Input over 64 KiB and sizes
  outside 2–500 columns or 1–300 rows are rejected without ending the session. A
  viewer that falls more than 1 MiB behind is detached.
- **Ending.** Ending a session sends `TERM` to the agent's process group, `KILL`
  after 5 seconds, and waits 5 seconds for the reap. Stopping Studio ends every
  session, attached or detached; nothing survives a restart.

The terminal client (xterm.js) is Studio's only browser library. Studio serves it
itself, and only with `--terminal`.

**Security model.** A terminal is shell-level access through the agent. It is
opt-in, requires the write path, and sits behind the token, the Host check, and
the Origin check. Taking over a session needs the same cookie as starting one.

## The Selections

A companion repository and a change. There is no working repository selection:
everything Studio serves is companion-scoped, so there would be nothing for one
to filter.

- the companion selection lists every registered companion repository
- a companion whose health is not ready stays listed, de-emphasized and
  annotated with the reported reason
- the selected companion's linked working repositories are shown beneath it as
  context, marking any repository that is also paired with another companion
- the change selection fills the workflow prompts. It also offers naming a
  change that does not exist yet, so a companion with no active change still
  shows a usable workflow; unnamed, the prompts carry a `<change-name>`
  placeholder

Studio reports health; it does not repair it. Use `mate doctor` for that.

## URL State

Both selections, the active view, and an open vault file live in the request URL,
so requesting a URL renders exactly the state it names:

```text
http://localhost:53219/?companion=9f2c14ab07&change=add-acme-checkout&view=vault&path=docs%2Fnotes.md
```

Changing a selection or switching a view is a navigation. The served page is
already correct for what was asked, deep links work, and the browser's back and
forward buttons move between states that have been rendered.

A companion is addressed by a short digest of its path rather than by the path
itself, so absolute companion paths are not written into the browser's address
bar, history, or autocomplete. The page names the selected companion in full, so
the URL never has to be read. A URL naming no companion, or a digest that
resolves to no registered companion, renders the selector with nothing selected
rather than failing the request.

## The Views

**Dashboard** shows the selected companion's changes — completed and total task
counts, status, and per-artifact state — and its specs grouped by the areas they
bind. A section with nothing to show says so explicitly.

**Workflow** presents the prompts a change is driven by, in order, one card per
prompt. Each card carries two colored boxes — **What** states the action the
stage performs, **Why** states the reason it sits at that position in the
sequence — plus the prompt itself and a control that copies it.

**Vault** lists every non-ignored markdown file under the selected Companion
Repository and opens one file in a plain textarea. Add `--writable` to either
invocation to show the save control. Saves carry a content version token; a
stale save is refused with both versions available for reconciliation. The
vault watches the selected companion and offers external changes to the open
editor without replacing unsaved content.

The workflow is a built-in sequence, not a scan of skill directories on disk:

- an optional grilling/questionnaire step appears before `explore`, asking 3-5
  high-leverage questions through the `/grill-me` or `/interview-me` skills
- `openspec explore` uses `/openspec-explore` to frame the change
- `openspec propose` uses `/openspec-propose` to create the selected profile's
  artifacts: proposal, specs, design, and tasks for `mate-v1`; only specs and
  tasks for `mate-minimal`
- `openspec apply` uses `/openspec-apply-change` to implement those tasks
- an optional `mate simplify code` step uses `/mate-simplify-code` after
  implementation, with a reminder to preserve behavior and rerun tests
- `/mate-artifact-publish` selects archived changes and runs
  `mate artifact finish` for each after confirming that each will be committed,
  tagged, and pushed to the companion Git repository; the command archives the
  change and applies its delta specs to the main specs, making it the only
  sanctioned completion
- the panel beside the deck carries the selected change's task counts and
  per-artifact state

Studio presents these optional actions as guidance; it does not inspect or
execute installed skills.

Every view is rendered on the server for the URL that requested it, so the
response already carries the content and nothing is fetched after the page
loads.

Reading a Companion Repository runs the OpenSpec CLI, so Studio reads each
companion once and keeps what it read for as long as the server runs. Selecting
a companion for the first time takes about a second; switching between the
Overview and the Workflow view after that is immediate, and both views show the
same reading. The rail names the time that reading was taken.

`Refresh` reads the selected companion again and replaces what Studio holds.
Dashboard and Workflow still do not watch the file system. The Vault watches
markdown files; if watching is unavailable, it reports that the tree may be out
of date and offers an explicit tree refresh.

## Appearance

The page ships a dark and a light theme from one palette. It follows the
system preference by default; the theme control in the rail cycles system,
dark, and light, and the choice is remembered in the browser. Nothing about the
theme is written to a companion or to Mate state.

## Reading the Same Data Elsewhere

Studio answers HTML only. Earlier versions also served `/api/inventory` and
`/api/companion`; both are gone, and a request for either is unrouted. They
existed to feed a browser-side renderer that no longer exists.

The aggregate inventory Studio projects its view from has no supported
machine-readable interface. `mate workspace list --json` used to be that
interface and has been removed along with the `mate workspace` namespace; the
inventory is now a private in-process library that only Studio reads.

A companion's own state is still reachable:

- the OpenSpec CLI reports a companion's state directly, through the same calls
  Studio makes against it: `openspec list --json`, `openspec list --specs
--json`, `openspec status --all --json`, and `openspec validate --json`

## Lifecycle

Studio is a foreground server, read-only by default:

- it binds a port the operating system assigns, on the loopback interface only,
  so two invocations never collide and nothing off this machine is served
- without `--writable`, no request writes to a companion repository, a working
  repository, or any Mate state
- the document is rendered on the server and carries its styles and its behavior
  inline, so it loads nothing from any external host and needs no build step;
  with `--terminal` it also loads the terminal client Studio serves itself
- `Ctrl+C` ends it; nothing outlives the invocation, so there is no stop
  subcommand, no process-identifier file, and no state written anywhere

The lifecycle above describes plain `mate studio`. `mate studio serve` uses its
required port and selected host, does not open a browser, and also exits cleanly
when interrupted or terminated.

`--writable` opts the Vault into writing only markdown inside the selected
companion; no Working Repository or Mate state is written. Unsaved editor
content is confirmed before file, view, companion, refresh, browser-leave, or
reload navigation.

The save check is optimistic, not a filesystem compare-and-swap. A write that
lands inside the vault's comparison-to-write window can be overwritten. When
the watcher observes that version, Studio reports the overwrite and keeps its
content available for recovery; an unobserved overwrite is not invented.
