title: Service Plugins
description: "Run a service next to Mate from a plugin: its own command, a background daemon, and Studio routes, views and terminal sessions."
---

A Mate plugin usually adds content to agent sessions: capabilities, hooks,
subagents. A **service plugin** also runs something next to Mate: a daemon
that Studio talks to, with its own command and its own part of Studio.

A plugin declares its service in `service` on the plugin object it returns.
Import the types from `@uniqbit/mate-core/plugin-api`, as types only: a
dynamically loaded plugin must not import runtime values from Mate.

```ts
import type { CreatePlugin, PluginService } from "@uniqbit/mate-core/plugin-api";

const createPlugin: CreatePlugin = () => {
  const service: PluginService = {
    apiVersion: 1,
    id: "acme",
    label: "Acme",
    command: { name: "acme", usage: ["acme serve --socket <path>"], run: serve },
    connection: (env) => (env.ACME_SOCKET ? { kind: "socket", path: env.ACME_SOCKET } : null),
    studio: (host) => ({
      routes: [
        {
          path: "/status",
          methods: { GET: { kind: "read" } },
          handle: async () => Response.json(await statusFrom(host.connection)),
        },
      ],
      views: [
        {
          id: "board",
          label: "Acme",
          module: { dir: "/opt/acme/studio", entry: "board.js" },
          attention: "/waiting",
        },
      ],
    }),
  };
  return {
    id: "acme",
    kind: "integration",
    label: "Acme",
    description: "Runs the Acme daemon",
    defaultSelected: false,
    selectable: false,
    isEnabled: () => false,
    async apply() {},
    async teardown() {},
    service,
  };
};

export default createPlugin;
```

Every part of a service is optional.

## Version

`apiVersion` names the service contract the plugin was written for. This Mate
supports version `1`. A service with a version Mate does not support is left
out with a warning on stderr; the rest of the plugin still loads. The version
grows only with a breaking change; new optional fields keep it.

`id` is lowercase kebab-case and names the service's routes and views. When
two plugins declare the same id, the first registered wins and the second is
left out with a warning.

## Command

`command` adds a top-level command, `mate <name> …`. Mate hands `run` every
argument after the name. A built-in command of the same name always wins. The
command runs without the companion and installation checks other commands
need, so a supervisor can start a daemon with it. Its `usage` lines appear in
Mate's help.

## Daemon connection

`connection` reads where the daemon listens from the environment Studio starts
in, as a Unix socket path or a URL. When it returns `null`, the daemon is not
there: Studio leaves the whole service out, its views and routes included. A
service without `connection` has no daemon and is always mounted.

## Studio

Studio calls `studio(host)` once when it starts, for each service whose
daemon is there. A service that throws is left out with a warning; Studio keeps
serving. The `host` gives the service:

| Field                       | What it is                                                                             |
| --------------------------- | -------------------------------------------------------------------------------------- |
| `connection`                | The resolved daemon connection, or `null`.                                             |
| `writable`, `noGit`         | Studio was started with `--writable`, or with `--no-git`.                              |
| `launchCompanion`           | The companion Studio was started for, when pinned.                                     |
| `mateCommand`               | The Mate invocation, for an argv the service hands the terminal.                       |
| `companionPath(digest)`     | The registered companion a page names; throws for an unknown one.                      |
| `companionSnapshot(digest)` | The companion's collected payload as Studio's views read it; `refresh` collects again. |
| `launchTarget(digest)`      | The companion a terminal session for that page runs in.                                |
| `boardChanged(path)`        | Tells open pages that the companion's Workset board changed.                           |
| `reports`                   | Publishes a hosted report for a companion, and lists its ids.                          |
| `terminal`                  | Studio's terminal sessions: which Worksets have one, when one ends, and ending one.    |

### Routes

A route answers below `/api/plugins/<id>/`. Its `path` starts with `/`; a
trailing `/*` also matches every deeper path. Each method names its guard,
which Studio checks before the route runs:

- `read`: Studio's access token, where reading needs it.
- `write`: a request from Studio's own page with its token. With `writable`
  set, Studio must also run with `--writable`; otherwise it refuses with that
  text.
- `socket`: a WebSocket, guarded like a write. `socket(request)` returns the
  handler that receives the connection, or `null` to refuse it.

`HEAD` follows `GET`. A method the route does not declare gets 405. A route of
a service that is not mounted gets 404. `context.keepOpen()` lifts Studio's
idle timeout for a long answer such as server-sent events.

### Views

A view is listed in Studio's navigation under **Services**. With `module`,
Studio serves the files in `module.dir` at
`/studio/plugins/<id>/<view id>/` and mounts `module.entry` at
`/plugins/<id>/<view id>`. Studio serves only files inside `dir`.

The entry is a browser ES module with a `mount` export:

```ts
import type { StudioViewMount } from "@uniqbit/mate-core/plugin-api";

export const mount: StudioViewMount = (element, { companion, apiBase, writable }) => {
  element.textContent = `Acme for ${companion ?? "no companion"}`;
  // Fetch your routes from apiBase, e.g. `${apiBase}/status`.
  return () => element.replaceChildren();
};
```

The module owns everything inside `element` and brings its own framework and
styles. Studio mounts it again when the selected companion changes, and calls
the returned function when the view leaves.

A view can name an `attention` route: a `read` GET route of the service, as a
path below its prefix, that answers `{ "count": <number> }` for
`?companion=<digest>`. Studio shows a count above zero on the view's
navigation entry and asks again when the companion's Workset board changes.

### Workset terminal sessions

`worksetSessions` lets Studio's terminal open a session for a Workset: the
browser names only the Workset, and `resolve` answers the argv to run, or a
reason to refuse. `onExit` hears when the agent in such a session quits by
itself. The first mounted service that offers it owns Workset sessions.

### Companions by URL

`companions` lets Studio add a companion by Git URL: `addByUrl` fetches it into
`folder`, and Studio registers it. Studio then deletes companion folders only
inside `folder`; a companion elsewhere is only removed from the list.
`pinnedCompanions` names companions Studio must not delete while the service
runs for them.

## Packaging

Declare the plugin package in the companion's `framework.yaml` under
`plugins:` and install it with `mate plugin install`, like any plugin. A
distribution can also register it in `createMate`.
