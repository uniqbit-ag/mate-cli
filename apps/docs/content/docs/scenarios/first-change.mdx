## Audience

Developers whose companion has the OpenSpec capability enabled and who want to
deliver a change the way Mate expects: planned, reviewed by people, implemented
on a branch, and published only once it is merged.

## Goal

Know which stage comes next, which skill or command drives it, and what Mate
waits for before your specs reach your teammates.

## The Delivery Path

Each **stage** names an action. A stage is driven by a **Mate skill** you invoke
in your agent, by a **person** (the reviews), or is optional. Mate skills follow
OpenSpec's workflows, which ship inside them, and call the **Mate CLI**
(`mate artifact …`) for the deterministic parts. You only ever invoke the Mate
skills listed here.

### Invoking a skill

How you type a skill depends on your agent runtime. Mate skills write their
handoffs in the syntax of the runtime you are using:

| Agent runtime       | Syntax        | Example                                 |
| ------------------- | ------------- | --------------------------------------- |
| Claude Code, Cursor | `/name`       | `/mate-propose-change acme-queue`       |
| OpenCode            | `@name`       | `@mate-propose-change acme-queue`       |
| Codex               | `$name`       | `$mate-propose-change acme-queue`       |
| Pi                  | `/skill:name` | `/skill:mate-propose-change acme-queue` |

Skills and this page write invocations as `/name`. A skill swaps only the
prefix when it knows your runtime, because you said which one you use or the
runtime identifies itself; otherwise it keeps `/name`, such as
`/mate-propose-change acme-queue`. In another runtime, type its prefix instead.

This table is invocation syntax only. It adds no Mate runtime integration:
Mate's launch and setup support stays as described in
[Capabilities](/docs/capabilities#skill-locations).

The full schema, `mate-v1`, writes a proposal, specs, a design, and tasks:

{/* delivery-path:mate-v1 */}

| #   | Stage                       | Driven by               |
| --- | --------------------------- | ----------------------- |
| 1   | Clarify intent (optional)   | `mate-clarify-intent`   |
| 2   | Explore change              | `mate-explore-change`   |
| 3   | Propose change              | `mate-propose-change`   |
| 4   | Review proposal             | you                     |
| 5   | Review specs                | you                     |
| 6   | Review design               | you                     |
| 7   | Review tasks                | you                     |
| 8   | Apply change                | `mate-apply-change`     |
| 9   | Inspect outcome (optional)  | `mate-show-me`          |
| 10  | Refine code (optional)      | `mate-simplify-code`    |
| 11  | Archive change              | `mate-archive-change`   |
| 12  | Publish companion artifacts | `mate-publish-artifact` |

The minimal schema, `mate-minimal`, writes only specs and tasks, so it has two
reviews:

{/* delivery-path:mate-minimal */}

| #   | Stage                       | Driven by               |
| --- | --------------------------- | ----------------------- |
| 1   | Clarify intent (optional)   | `mate-clarify-intent`   |
| 2   | Explore change              | `mate-explore-change`   |
| 3   | Propose change              | `mate-propose-change`   |
| 4   | Review specs                | you                     |
| 5   | Review tasks                | you                     |
| 6   | Apply change                | `mate-apply-change`     |
| 7   | Inspect outcome (optional)  | `mate-show-me`          |
| 8   | Refine code (optional)      | `mate-simplify-code`    |
| 9   | Archive change              | `mate-archive-change`   |
| 10  | Publish companion artifacts | `mate-publish-artifact` |

Studio's Workflow view shows the same stages for both schemas. Each path is a
node graph running top to bottom: one node per stage, connected by edges in
stage order, beside labelled Plan, Review, Build, and Ship bands. The reviews
share one group node. Apply change branches to the optional Inspect outcome and
Refine code, which rejoin at Archive change. A dashed bypass edge skips each
optional stage, and a mark on an edge shows where a new session starts. An
inner frame marks the stages each change repeats, up to Archive change. An
outer frame holds the Workset: one or more changes delivered together on one
branch per Working Repository. Select a
node to open its stage in the side panel: what it does, why it is there, its
phase, and its prompt ready to copy.
To see where a change's delivery stands, run
`mate artifact pending`.

Every stage skill ends its handoff with a numbered **Next steps** section and
nothing after it. The list holds only the actions to take now, in order, with
exact commands and change names; a prerequisite comes before what depends on it.
Summaries, warnings, optional stages, and deferred slices stay above it. A
skill never runs an action just because it listed it, and a completed
publication ends without one. After propose in Claude Code, for example:

```text
Validation passed; validation is not approval.

## Next steps
1. Review specs: openspec/changes/acme-queue/specs/
2. Review tasks: openspec/changes/acme-queue/tasks.md
3. After your review: /mate-apply-change acme-queue
```

## Steps

### 1. Clarify intent (optional)

Run `/mate-clarify-intent about <idea>` when the idea is still vague. It checks
whether the request states who it is for, why it is needed now, how success is
measured, and what constrains it, then picks one mode: an interview when
something is missing, grilling when a proposed direction needs testing, or
nothing for a small, fully specified change. Reply `interview`, `grill`, or
`skip` to override. You can also start `/mate-interview-me` or `/mate-grill-me`
directly. All three end with a handoff to the next stage and write no files.

### 2. Explore change

`/mate-explore-change for <change-name>` investigates the repository with the
scope your companion's context map assigns to the Working Repository and Area.
When the feature is too big for one change, it suggests slices.

### 3. Propose change

`/mate-propose-change for <change-name>` chooses the schema. It uses
`mate-minimal` only when intent and scope are clear, the change stays in one
Area, and it is low risk: no new dependency, no data-model or public API change,
and no security, performance, or migration concern. Public API includes command
names, flags, exit codes, JSON output fields, config keys, and exported package
symbols. Otherwise it uses `mate-v1`.
One prompt writes every artifact of the chosen schema.

When you skipped explore, propose applies the same slicing test first, unless
you already decided to keep one change. The test passes only when the feature
holds several behaviours that can each ship and be reviewed on their own, or more
work than one review can hold (roughly more than 20 tasks or 800 changed lines).
Several Areas alone are no reason to slice: they stay one change with a scope
per Area. When the test clearly passes, propose suggests slices and writes
nothing until you agree or keep one change; when the slice boundaries are
unclear, it points you back to explore. A borderline case stays one change:
propose says why in one line and goes on.

### 4. Review the artifacts yourself

Reviews have no skill and no prompt. Read each artifact in schema order and
edit it until you agree with it. To fold a decision into every affected
artifact at once, run `/mate-propose-change for <change-name>` and ask for the
revision: for an existing change it proposes the edits and writes each one after
you confirm. Mate shows whether each artifact exists and
whether the change validates, but it never records or claims an approval, and a
passing validation is not a review.

### 5. Apply change on a delivery branch

`/mate-apply-change for <change-name>` first records the **delivery branch**:
the Working Repository branch your change is merged through. Its default is
`workset/<workset-id>`, or `workset/<TICKET>-<workset-id>` when you give a ticket
as the branch is created; a team can change that naming with a branch template
(below). A Workset groups changes delivered in one merge per
repository. A standalone change has an implicit single-change Workset whose id
is its change name; no Workset record is written. A slice whose `dependsOn`
change records a branch that is not merged yet continues on that branch, so the
slices of one feature share one merge. On the recorded branch or the resolved
delivery branch, apply continues without asking. On any other branch,
protected or not, it shows one menu: create or switch to the delivery branch
(recommended), create a worktree, use the current branch (only when it is not
protected), use or create another branch you name, or work directly (only on a
protected branch, on explicit choice). Apply records a branch you name before it
creates it, so a refused name leaves no branch behind. With Jira tickets, a
branch you name carries its ticket only in its name, such as
`feature/ABC-123-acme-retry`.

Existing recorded branches, including `change/*` and custom names, remain valid.
Regrouping a change never replaces its recorded branch: Mate reports the mismatch,
and relinking requires your confirmation. Ambiguous membership, identity collisions,
or invalid Workset records suppress unsafe defaults and ask you for a branch name.

On a **protected branch** it does not implement by default. A branch is
protected when it is the repository's default branch or matches a pattern configured on the
companion's openspec capability. Mate does not ask GitHub, so add a branch only
GitHub protects to the pattern list:

```yaml
# .mate/config/framework.yaml
capabilities:
  - name: openspec
    protectedBranches: ["release/*", "develop"]
```

Creating or switching to the default branch carries uncommitted edits over.
Whenever the menu shows, apply names local commits that are not pushed yet and
never moves them.

Tickets are off by default. Turn them on with `mate companion setup --ticket jira`,
or the wizard's Tickets step, which writes:

```yaml
# .mate/config/framework.yaml
capabilities:
  - name: openspec
    ticket: jira
```

With Jira on, a ticket only names a new branch: when the default branch does
not exist yet, you can add an optional key to your menu answer (`1 ABC-123`), and
the new branch or worktree is named after it; `1` alone creates it without one.
There is no separate ticket question. Mate stores the ticket
nowhere else; the branch name carries it. Started on a fresh, unprotected branch
whose name holds one key, such as `feature/ABC-123-retry` or `feature/abc-123-retry`
with no commits beyond `origin/HEAD`, apply records that branch without asking and
says so. Propose and archive never ask for a ticket.

A team with its own branch convention sets a **branch template** once, on the
same capability:

```yaml
# .mate/config/framework.yaml
capabilities:
  - name: openspec
    branchTemplate: feature/{ticket}-{workset}
```

`{workset}` is the Workset id and must appear once; `{ticket}` is optional.
Without a ticket, `{ticket}` and one separator next to it (`-`, `_`, or `/`) are
dropped, so the example names `feature/ABC-123-acme-retry` with a ticket and
`feature/acme-retry` without one. The template needs a fixed prefix ending in
`/`, such as `feature/`. An invalid template counts as the default
`workset/{ticket}-{workset}`, and `mate artifact link` reports why. Recorded
branches are never renamed, and unrecorded branches made under the default
template are still found after the switch.

Then apply implements the tasks. Open your PR whenever you
like; Mate does not open, merge, or push anything.

For a long task list you can ask for **compact apply**:
`/mate-apply-change for acme-queue with compact apply`. Apply then fetches its
instructions through `mate artifact apply-context`: a full baseline first, then,
after each task, only the current state of every task. The OpenSpec workflow,
its checks, and its default output stay unchanged, and every task still
re-fetches fresh instructions. After a new session, a resume, or context
compaction, apply omits `--since` and starts again from a full baseline, since a
remembered digest is not the context it stands for. Savings are measured in
bytes on fixed fixtures, not in tokens or billing.

A change whose scopes name several repositories needs a delivery for each one.
Apply records the Working Repository's; record each other repository with
`mate artifact link <change-name> --repository <org/repo> --branch <branch>`, or
`--not-applicable <reason>` when it needs no branch. Publication holds the
change back until every named repository has a delivery.

When the change declares `dependsOn` and a dependency is neither archived nor fully
implemented, recording the branch warns about it, so apply asks whether to apply
the dependency first. The warning never blocks.

### 6. Inspect and refine (optional)

`/mate-show-me` renders what the change did; `/mate-simplify-code` tidies it.
Either, both, or neither, in any order.

### 7. Archive change, before or after the merge

`/mate-archive-change for <change-name>` runs `mate artifact archive`, which
applies the delta specs to the local canonical specs, moves the change into the
archive, and leaves a `delivery.yaml` in it. **Archiving does not wait for the
merge**: while your PR collects approvals, the next change of the same feature
can already be written against the updated specs. Archiving is local and
uncommitted. It warns when another active change modifies the same requirement
when a change it `dependsOn` is not archived yet, or when a planning artifact its
schema requires is missing; warnings never block.

### 8. Publish companion artifacts after the merge

`/mate-publish-artifact` lists archived, unpublished changes and publishes the
ones you select with the `mate artifact publish` CLI: one commit, one tag, and
a push to the companion. It first settles each archive's delivery branch:

- With a [forge token](/docs/concepts/forge-token), it asks GitHub whether the
  branch's PR is merged.
- Without one, it asks you once per branch: **merged**, **not yet merged**, or
  **dropped**. Your answer is recorded as yours, and it points to the token
  setup once per run.

Only merged (or not-applicable) archives get a number. The rest stay in the list
marked **waiting for merge**, so the published specs always describe the
default branch. A dropped branch's archive can be restored with Git, because
nothing was committed yet.

## A Feature Delivered As Several Changes

Large features work best as several small changes:

1. Let explore suggest slices, or propose when you skipped explore, and propose
   one change per slice. A later slice declares `dependsOn: [<earlier-change>]`
   in its first artifact's frontmatter.
2. Group slices delivered in one merge into one Workset and apply them on
   `workset/<workset-id>`; each records it. A slice needing its own merge is a
   separate Workset connected by dependencies.
3. Archive each slice as soon as it is applied, so the next one builds on its
   specs.
4. After the feature PR merges, publish them together: one lookup or one answer
   settles every archive on that branch.

## Breaking Changes

{/* breaking:start */}

Two Mate skills were renamed without aliases, and `mate companion update`
removes the old copies Mate installed:

{/* breaking:renamed */}

- `mate-artifact-publish` is now `mate-publish-artifact`.
- `mate-openspec-backfill` is now `mate-backfill-spec`.

The generated OpenSpec skills (`openspec-*`) and commands (`/opsx:*`) are gone;
`mate companion update` removes them. Use the Mate skills instead:

{/* breaking:openspec */}

| Instead of                                 | Use                    |
| ------------------------------------------ | ---------------------- |
| `/opsx:explore`, `openspec-explore`        | `/mate-explore-change` |
| `/opsx:propose`, `openspec-propose`        | `/mate-propose-change` |
| `/opsx:apply`, `openspec-apply-change`     | `/mate-apply-change`   |
| `/opsx:update`, `openspec-update-change`   | `/mate-propose-change` |
| `/opsx:archive`, `openspec-archive-change` | `/mate-archive-change` |
| `/opsx:sync`, `openspec-sync-specs`        | `/mate-archive-change` |

`mate artifact publish` now refuses an archive whose delivery is not merged.
Archives made before delivery records existed still publish, with a warning
that their merge was not checked.

{/* breaking:end */}

## Result

Your change is archived, its delivery branch is merged, and its canonical specs
are published to the companion under their own tag. See the
[command reference](/docs/reference/commands#artifacts-and-updates) for every
`mate artifact` command.
