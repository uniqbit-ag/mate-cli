---
title: Design A Team Companion
description: Create the companion repository that sets how every agent on your team works.
---

## Audience

AI architects, platform engineers, and tech leads who decide how coding agents
work across a team. It also helps developers who own a companion for their own
repositories.

## Goal

Create a shared companion with the team's agents, capabilities, rules,
skills, and secret patterns, then roll it out so every teammate gets the same
setup with two commands.

## Steps

<Steps>
<Step>

### Create the companion repository

Create an empty repository on your Git host, for example `acme/acme-companion`,
and link it from one of the team's working repositories:

```sh
cd /path/to/acme-app
mate install
mate companion link
```

Choose **git** and paste the repository URL. Mate clones it to
`~/.mate/companions/acme-companion/` and runs setup on it, because it is not a
companion yet. To start from a local folder instead, see
[Create A Companion](/docs/getting-started/companion).

</Step>
<Step>

### Set the team policy

Setup decides which agents may launch, which capabilities everyone gets, and the
Git mode. To change the choices later, or to
keep them in a script you can review, run setup with flags from the companion:

```sh
cd ~/.mate/companions/acme-companion
mate companion setup \
  --allowed-agent claude \
  --allowed-agent opencode \
  --capability openspec \
  --capability tokensave \
  --git-mode auto
```

Use `auto` Git mode for a shared companion. Every launch then fetches and
merges the companion's upstream first, so teammates get your changes without
syncing by hand. Archive and publication also fetch the delivery branch before
checking whether it is merged; see [Merge State](/docs/concepts/merge-state). See [Capabilities](/docs/capabilities) for what each one adds.

</Step>
<Step>

### Write the team rules

`AGENTS.md` holds the instructions every agent reads. It starts with Mate's
defaults in a `MATE:COMPANION` block. Add your team's conventions below that
block: architecture boundaries, testing expectations, review rules, and
anything an agent keeps getting wrong. At every launch Mate refreshes only its
block and keeps your text.

</Step>
<Step>

### Add team skills

Put the team's own skills next to Mate's:

- `.claude/skills/<skill-name>/SKILL.md` for Claude Code.
- `.agents/skills/<skill-name>/SKILL.md` for OpenCode.

Mate manages only the skills it installs, so your skills are never overwritten
or removed when it refreshes its own. Mate's skills are local copies that Git
ignores, while yours are committed and shared. To change how a Mate skill
behaves for the team, copy it under a name of your own instead of editing it.

</Step>
<Step>

### Declare your workflow

Without a declaration, every change follows Mate's Delivery Path as described
in [Your First Change](/docs/scenarios/first-change). To add a check, a stage,
or your own skills, commit `.mate/config/workflow.yaml`. Setup, sync, and
`mate companion update` never touch this file.

```yaml
version: 1
stages:
  - id: explore
    steps: [{ skill: mate-explore-change }]
  - id: propose
    steps: [{ skill: mate-propose-change }, { skill: acme-plan-check }]
  - id: review
    review: schema
  - id: security-review
    label: Security review
    steps: [{ skill: acme-security-review }]
  - id: apply
    steps: [{ skill: mate-apply-change }, { skill: acme-verify }]
  - id: submit
    artifact: openspec
    steps: [{ skill: acme-pr-check }, { skill: mate-submit-change }]
  - id: publish
    steps: [{ skill: mate-publish-artifact }]
```

A declaration is a custom workflow: it lists every stage and takes nothing from
the default path. Without the file, the default path applies.

**Stages** are listed in path order. Each has a unique `id`, an optional
`label` and `optional: true`, and either `steps` or `review`. You may add,
remove, and reorder stages, but `submit` then `publish` end every path, are
never optional, and keep their Mate skills, because they push and publish the
change.

**`submit` names its artifact type** with `artifact:`: `openspec` for OpenSpec
changes, as above, or a type you declare, as in
[a fully custom path](#a-fully-custom-path). It is required; a custom workflow
never falls back to OpenSpec.

**Steps** are always `{ skill: <name> }` and run in order, each started by you.
Each Mate stage skill may
appear only in its own stage, once:

| Stage             | Mate stage skill        |
| ----------------- | ----------------------- |
| `clarify-intent`  | `mate-clarify-intent`   |
| `explore`         | `mate-explore-change`   |
| `propose`         | `mate-propose-change`   |
| `apply`           | `mate-apply-change`     |
| `inspect-outcome` | `mate-show-me`          |
| `refine-code`     | `mate-simplify-code`    |
| `submit`          | `mate-submit-change`    |
| `publish`         | `mate-publish-artifact` |

**Starting a stage.** A stage is started with the skill of its first step, as
`/<skill> <change>`: above, `/mate-apply-change acme-login` starts `apply`,
`/acme-security-review acme-login` starts `security-review`, and
`/acme-pr-check acme-login` starts `submit`. There is no wrapper skill, and the
default path is run exactly as before. A skill is one step of the whole
Delivery Path, so the skill you run identifies its stage.

**Steps are started by you.** Every step of a stage is run by the developer, one
at a time, like the stages themselves. Each Mate stage skill ends by running
`mate workflow done <skill> <change>`. The command records that step and
prints the hand-off: the next step of the stage while one is left, or the stage
the change is then at. Above, `/mate-apply-change acme-login` ends with
`/acme-verify acme-login` as its next step; nothing runs it for you. The default
path uses the same command.

**Your skills need no Mate line.** Declare a skill you already have as a step,
and leave it as it is. Mate adds one rule to the session's guidance: after
running one of your skills for a change, the session runs
`mate workflow done <skill> <change>` and ends with the hand-off it prints.
When a session misses that, the step still counts: once a later step of the
Delivery Path is recorded for the change, or the change is submitted, every
earlier step nobody reported counts as done. Starting the next step is you
saying the earlier one is finished. A counted step is never an action again; the
hand-off names it in one line above its section,
`Counted, not reported: /acme-security-review acme-login. Not an action below; run it if it did not run.`,
and submit names it in a `step-counted` warning. Tell `/mate-apply-change` or
`/mate-submit-change` that an earlier step ran, and it records it. A skill whose
author ends it with `mate workflow done` anyway is recorded like any report.

**In Claude Code, a turn hook checks the end of each step**, in a session Mate
launches and in one you start with `claude` in a wrapped repository. It notes
the step a turn starts and whether the session reported it. When the session
reported a step but its response has no `## Next steps` section, or a section
that leaves out an action `mate workflow next` prints or adds a later step of
the change it does not print, the hook sends it back once with the actions to
list. When the turn started a skill of your
own and the session never reported it, the hook asks once to report it if the
skill has finished. The hook records nothing itself, never sends a turn back
twice, and stays silent in a turn that starts no step. Set `MATE_TURN_HOOKS=off`
to turn it off.

**In OpenCode, Mate's plugin runs the same check.** When a turn ends
successfully and the hook would send it back, the plugin adds one message marked
"Mate hand-off check" with the same request, and the session continues. A
failed or interrupted turn, a subagent's turn, and a turn after which you have
already typed the next prompt get none. `MATE_TURN_HOOKS=off` in the
environment OpenCode runs in turns it off. Other runtimes rely on the guidance
rule and counting alone.

A skill appears at most once in the Delivery Path's `steps`.

**A step skill** receives the user's request and the change name, and the chosen
schema in `propose`. It does its work and stops: the command names what follows,
so a hand-off the step proposes is ignored.

**Review stages** set `review: schema` to review every planning artifact of the
change's schema, or list artifact ids such as `review: [proposal, specs, tasks]`.
An artifact the change does not have is skipped. A review stage has no steps:
people review.

**Progress.** Each finished step is recorded in the change's `delivery.yaml`,
as a list per stage:

```yaml
stages:
  security-review: [acme-security-review]
  apply: [mate-apply-change, acme-verify]
```

A stage is done when every step it declares is done and, for `propose` and
`apply` of an OpenSpec change, its plan agrees: the change has tasks, and for
`apply` every task is checked. A step of your own is done once it is recorded,
or counted because a later step is recorded. A Mate stage skill's step is done
once the plan says its work is done, recorded or not, so a session that ended
without reporting it blocks nothing, and changes begun earlier keep their
place. A step reported out of order is still recorded, and the steps before it
count. A step you add later
reopens the stage until it is recorded; a step you remove is ignored. A change
is at its first stage that is neither optional nor done, and Studio places it
there. You never run these commands yourself: the skills run them, and each
skill's response ends with the next actions.

**Submit warns about an unfinished change.** `mate artifact submit` adds a
`stage-open` warning while the plan leaves a required stage before `submit`
open (open tasks, or none), naming the stage, what is open, and the skill to
run. Submitting counts every other step before `mate-submit-change` nobody
reported, and names them in a `step-counted` warning. The change is still
submitted.
Mark a stage `optional: true` when a change may skip it, or when it ends before
the change folder exists and so cannot be recorded. The recorded steps stay in
the change's `delivery.yaml` when it is published, as a trace of what was run.

**Validation** is strict: unknown keys, duplicate keys, anchors, and aliases are
errors, and an invalid file stops every stage instead of falling back to the
default. `mate workflow steps <stage>` reports each problem with its key path,
such as `stages[3].steps[1].skill`.

#### A fully custom path

A companion that does not plan with OpenSpec declares its own artifact type and
names it on `submit`:

```yaml
version: 1
artifacts:
  acme-notes:
    change: notes/{name}/
    published: [notes/index.md]
    archive: notes-history/{id}/
    reviews: { brief: brief.md, plan: plan.md }
    submit:
      check: { run: "acme-notes lint {change}" }
    publish:
      apply: { run: "acme-notes merge {change}" }
      validate: { run: "acme-notes verify {files}" }
stages:
  - id: draft
    steps: [{ skill: acme-draft-plan }]
  - id: plan-review
    review: [brief, plan]
  - id: build
    steps: [{ skill: acme-build }]
  - id: submit
    artifact: acme-notes
    steps: [{ skill: mate-submit-change }]
  - id: publish
    steps: [{ skill: mate-publish-artifact }]
```

- `change` is the folder of a change while it is worked on and after it is
  submitted; Mate keeps its `delivery.yaml` there. A skill of yours creates the
  folder.
- `published` lists the files publication writes. Agents read these as current,
  and never a submitted folder unless you name it.
- `archive` is optional. With it, publication moves the change's folder there
  as history; without it, the folder is deleted.
- `reviews` names the files a review stage can list.
- `submit.check`, `publish.apply` (required), and `publish.validate` are
  commands run with `sh -c` in the companion. `{name}`, `{id}`, `{change}`,
  `{archive}`, and `{files}` are replaced by shell-quoted values, and a
  non-zero exit fails the step. `publish.apply` may change only `published`
  files; Mate moves or deletes the change folder itself.
- Each developer approves these commands once on their machine with
  `mate workflow trust`, in a terminal. Until then submit and publication
  refuse to run them, since anyone who can push to the companion can change
  them. An edited command needs approving again.

The paths must stay inside the companion, outside `.mate/`, and must not
overlap each other or OpenSpec's folders. With no Mate apply skill on the path,
`/mate-submit-change` asks once which branch delivers the change.

</Step>
<Step>

### Name your branches

Mate names a change's delivery branch `workset/<workset-id>`, or
`workset/<TICKET>-<workset-id>` with a Jira key. If your team has its own
convention, set a branch template on the openspec capability in
`.mate/config/framework.yaml`:

```yaml
capabilities:
  - name: openspec
    ticket: jira
    branchTemplate: feature/{ticket}-{workset}
```

`{workset}` must appear once and `{ticket}` is optional; the template needs a
fixed prefix ending in `/`. This example names `feature/ABC-123-acme-retry`, or
`feature/acme-retry` without a ticket. Existing branches keep working after the
switch. See [Your First Change](/docs/scenarios/first-change) for the details.

</Step>
<Step>

### Tighten the secret guardrails

The [secret guardrails](/docs/concepts/secret-guardrails) are on by default.
Add patterns for the secret files your repositories use in the companion's
`.mate/config/framework.yaml`:

```yaml
secrets:
  deny: ["config/master.key.enc"]
  allow: [".env.test"]
```

Extra patterns are added to the defaults and never replace them.

</Step>
<Step>

### Try it, then push

From the working repository you linked first, check the setup and start a
session:

```sh
mate doctor
mate claude
```

When the agent behaves the way you want, commit and push the companion:

```sh
cd ~/.mate/companions/acme-companion
git add -A
git commit -m "Set up team companion"
git push
```

</Step>
<Step>

### Roll it out

Each teammate runs this once in each of their working repositories:

```sh
mate install
mate companion link
```

They choose **git** and paste the same URL. From then on, everyone launches
with `mate claude` or `mate opencode`, and every change you push to the
companion reaches them on their next launch.

</Step>
</Steps>

## Outcome

The team's agent setup lives in one reviewed repository: allowed agents,
capabilities, rules, skills, and secret patterns. Changing how agents work is
a commit to the companion, not a change in every product repository. To use
the same companion across several codebases, see
[One Companion, Many Repositories](/docs/scenarios/one-companion-many-repos).
